나의쿠키는 개발자 취업 준비생을 위한 학습 사이트입니다. 처음에는 화면과 API, DB 정도만 있는 작은 서비스였고, 코드를 고치면 직접 확인하고 배포하는 것으로 충분했습니다.

서비스가 커지면서 사정이 달라졌습니다. 클라우드에서 홈서버로 옮기면서 직접 운영할 것이 늘었고, Redis와 Kafka가 들어왔고, 하루에도 여러 번 배포하게 됐습니다. 그런데 어떤 변경이 안전한지, 테스트를 돌렸는지, 운영에서 문제가 생겼을 때 언제 알게 되는지는 여전히 사람의 기억에 맡기고 있었습니다.

그래서 개발 워크플로를 처음부터 설계하고 적용했습니다. 이 글은 그 과정에서 세운 원칙, 실제로 적용한 방법, 적용한 뒤 달라진 점을 정리한 기록입니다.

1. 설계: 네 가지 원칙

도구를 고르기 전에 원칙부터 정했습니다. 이후의 선택은 모두 이 네 가지를 기준으로 했습니다.

원칙 이유
모든 일은 이슈에서 시작한다 머릿속에만 있는 일감은 빠지고, 누가 하는지 알 수 없다
확인은 기계가 먼저, 사람은 위험한 곳에만 모든 변경에 사람의 승인을 요구하면 승인이 형식이 된다
운영으로 가는 길은 하나 스테이징을 거치지 않은 코드가 운영에 들어가지 않게 한다
알림은 할 일이 생길 때만 할 일이 없는 알림이 쌓이면 중요한 알림을 놓친다

2. 워크플로 한눈에 보기

그림 1. 이슈 등록부터 운영 배포, 장애 알림까지의 흐름

단계 사람이 하는 일 자동으로 되는 일
이슈 할 일을 적는다 담당자 지정, 사용자 제보는 이슈로 자동 등록
PR 작업 브랜치에서 dev로 올린다 CI, 위험도 판정, 알림
병합 위험도에 따라 승인한다 낮은 위험도는 자동 병합
배포 운영 병합은 관리자가 누른다 dev는 스테이징, master는 운영에 5분 안에 배포
운영 알림을 보고 대응한다 고위험 오류 감지, AI 요약

사람의 손이 필요한 곳은 할 일 적기, 위험한 변경 승인, 운영 배포 결정, 장애 대응 네 가지뿐입니다. 나머지는 GitHub Actions와 서버가 맡습니다.

3. 적용

3-1. 이슈: Jira 대신 GitHub 이슈

일감 관리 도구로 Jira도 고민했습니다. 하지만 작은 팀에서는 도구가 하나 늘어나는 비용이 더 크다고 봤습니다. 코드, PR, CI가 모두 GitHub에 있으니 이슈도 같은 곳에 두는 편이 낫습니다. PR 본문에 closes #12를 적으면 병합할 때 이슈가 자동으로 닫히는 것처럼, 한곳에 있어서 얻는 이점이 컸습니다.

  • 이슈는 "기능", "버그" 양식으로 등록하고, 제목 머리말과 라벨이 자동으로 붙습니다.
  • 새 이슈와 PR의 담당자는 관리자로 자동 지정됩니다. 담당자가 비어 있는 일감이 생기지 않게 하기 위해서입니다.
  • 사용자가 사이트에서 보낸 버그 제보도 GitHub 이슈로 자동 등록됩니다. 사용자 제보와 내부 일감을 한곳에서 봅니다.

사용자 제보를 이슈로 만드는 작업은 Kafka 이벤트로 처리합니다. 제보를 저장한 뒤 이벤트만 넣고 바로 응답하고, 이슈 생성과 알림은 소비자가 맡습니다. GitHub이나 Mattermost가 느리거나 실패해도 사용자의 제보 요청은 영향을 받지 않습니다.

그림 2. 실패하면 10초 간격으로 세 번 다시 시도하고, 그래도 안 되면 DLT에 남긴다

다시 시도할 때 같은 이슈가 두 번 만들어지면 안 되므로, 이슈 번호와 알린 시각을 단계마다 DB에 기록해 이미 끝난 단계는 건너뜁니다. Kafka가 멈추면 예전처럼 요청 안에서 바로 처리하도록 우회로도 남겼습니다.

3-2. PR과 CI: 기계가 먼저 확인한다

GitHub Actions로 PR마다 두 작업을 돌립니다.

작업 내용
백엔드 테스트 전체 테스트. 스프링 컨텍스트가 실제로 뜨는지, Testcontainers로 PostgreSQL, Redis, Kafka를 띄운 통합 테스트까지 포함
화면 검사 린트, 빌드, 문제 데이터 검사

CI를 붙이는 과정에서 운영에 숨어 있던 버그를 찾았습니다. 실시간 대결은 서버가 정답표로 채점하는데, 최근 추가한 문제 27개가 정답표에서 빠져 있었습니다. 데이터 검사 스크립트는 예전부터 있었지만 아무도 돌리지 않았기 때문에 발견되지 않았습니다.

같은 커밋이 한 번은 통과하고 한 번은 실패하는 테스트도 있었습니다. Kafka 소비자는 알림을 보낸 뒤 "알린 시각"을 저장하는데, 테스트가 알림 호출만 확인하고 곧바로 DB를 읽고 있었습니다. 저장이 끝날 때까지 기다리도록 고쳤습니다. 이런 실패를 다시 돌리기만 하면 팀이 CI의 빨간 표시를 믿지 않게 되므로, 원인을 끝까지 찾는 것을 원칙으로 했습니다.

3-3. 위험도 규칙: 사람의 확인은 위험한 곳에만

모든 PR에 승인을 요구하는 대신, 변경을 위험도로 나눴습니다. 위험도는 사람이 판단하지 않습니다. PR에서 바뀐 파일 경로를 보고 GitHub Actions가 자동으로 정하고, PR에 라벨을 붙입니다.

그림 3. 바뀐 파일로 위험도를 정하고, 위험도마다 병합 조건이 다르다

DB 엔티티를 높음으로 둔 데는 이유가 있습니다. 나의쿠키는 아직 JPA의 ddl-auto: update로 스키마를 관리해서, 엔티티 필드 하나를 바꾸면 배포와 동시에 운영 테이블이 바뀝니다. 엔티티 코드 리뷰가 사실상 스키마 리뷰입니다.

위험도 검사는 PR의 필수 검사로 등록했습니다. 조건을 채우지 못하면 검사가 실패하고, GitHub의 브랜치 규칙(Rulesets)이 병합 버튼을 막습니다. 승인이 들어오면 검사가 다시 돌아 통과합니다. 판정 이유는 검사 요약에 남겨서 왜 막혔는지 PR 화면에서 바로 알 수 있습니다.

설계하면서 부딪힌 문제가 하나 있었습니다. 운영 배포에 관리자의 승인을 받게 하려 했는데, GitHub에서는 자신이 올린 PR을 스스로 승인할 수 없습니다. 관리자가 직접 dev → master PR을 올리면 영원히 막힙니다. 그래서 "관리자의 승인"을 "관리자만 병합할 수 있음"으로 바꿨습니다. master의 업데이트 권한을 관리자에게만 열어 두면 누구나 PR을 올릴 수 있지만 병합은 관리자만 합니다.

중간 위험도 PR을 AI가 리뷰하고 자동 병합하는 방식도 검토했지만, PR마다 유료 API 비용이 발생해 넣지 않았습니다. 개인이 운영하는 서비스에서 고정 비용이 계속 늘어나는 구조는 맞지 않다고 판단했습니다.

3-4. 알림: 할 일이 생기는 것만

알림 채널은 매일 쓰는 SSAFY Mattermost에 만들었습니다. 일반 사용자가 웹훅을 만들 수 있는지 확실하지 않아서 작은 검증(PoC)부터 했습니다. 팀 메뉴에는 "통합" 항목이 보이지 않았지만, 통합 페이지 주소로 직접 들어가니 수신 웹훅을 만들 수 있었습니다.

연결 직후에는 PR을 병합할 때마다, 이슈를 닫을 때마다 알림이 왔고 채널이 금방 시끄러워졌습니다. 그래서 원칙대로 "받은 사람이 지금 무언가 해야 하는가"를 기준으로 걸렀습니다.

알림 할 일 결정
사용자 버그 제보, 기능 요청 확인하고 담당자 정하기 보냄
새 이슈 작업 시작 보냄
PR 열림 리뷰 보냄
CI 실패 바로 수정 보냄
PR 병합, 이슈 닫힘 없음 보내지 않음

그림 4. 리뷰 요청, 새 이슈, CI 실패, 고위험 장애 알림이 한 채널로 온다

3-5. 장애 알림: 정말 급한 것만, 바로 대응할 수 있게

마지막으로 사이트가 멈추거나 오류가 몰릴 때 바로 알 수 있게 했습니다. 모든 오류를 알리면 다시 채널이 시끄러워지므로 대상은 세 가지로 좁혔습니다.

상황 기준 감지
치명 오류 메모리 부족, DB 연결 실패처럼 서비스 전체를 멈출 수 있는 오류는 한 번만 나도 백엔드
오류 급증 5분 동안 ERROR 로그 10건 이상 백엔드
사이트 다운 1분마다 확인해 3번 연속 응답이 없을 때 홈서버의 점검 스크립트

그림 5. 서버가 통째로 죽는 경우는 백엔드가 알릴 수 없으므로 홈서버가 바깥에서 확인한다

알림에는 무료로 쓸 수 있는 Gemini API로 "무슨 일, 영향, 의심 원인, 먼저 볼 곳, 바로 할 조치" 다섯 줄 요약을 붙입니다. 다만 AI 요약은 틀릴 수 있으므로 오류 이름, 발생 건수, 발생 시각, 코드 위치를 원본 그대로 함께 보냅니다. 요약은 어디부터 볼지에 대한 힌트이고, 판단은 원본 증거로 합니다.

무료 등급에서는 입력한 내용이 서비스 개선에 쓰일 수 있어서, 보내기 전에 이메일, IP, 토큰, 비밀번호 같은 값을 가립니다. 같은 문제는 30분에 한 번만 알리고, 이 기록은 Redis에 둬서 서버를 다시 띄워도 유지됩니다.

4. 적용한 뒤 달라진 점

워크플로를 적용한 첫날부터 효과가 보였습니다.

  • CI가 바로 문제를 잡았습니다. 대결 정답표 누락, 저장소에서 빠져 있던 빌드 스크립트의 실행 권한, 결과가 그때그때 다른 테스트를 병합 전에 찾았습니다.
  • 규칙을 들인 PR이 그 규칙에 막혔습니다. 위험도 규칙을 추가한 PR은 작업 브랜치에서 master로 바로 올라가 있었고, CI 설정을 바꾼 높은 위험도 변경이었습니다. 새 규칙은 이 PR에 빨간 표시를 띄웠습니다. 규칙을 처음 도입하는 PR만 관리자 예외로 병합하고, 이후 PR은 모두 dev를 거치게 했습니다.
  • 할 일이 채팅으로 왔습니다. 리뷰 요청, 새 이슈가 알림 채널에 바로 올라왔고, 담당자도 자동으로 지정됐습니다.
이전 이후
테스트는 기억날 때만 모든 PR에서 전체 테스트 자동 실행
모든 변경을 같은 방식으로 병합 위험도에 따라 자동 병합부터 승인 필수까지
운영 배포는 누구나 dev를 거쳐 관리자만 병합
일감은 머릿속에 GitHub 이슈, 담당자 자동 지정
장애는 사용자가 알려 줄 때 앎 고위험 오류는 AI 요약과 원본 증거를 담아 바로 알림

5. 마치며

돌아보면 새 도구를 들인 것보다 무엇을 사람이 하고 무엇을 기계에 맡길지 정한 것이 더 중요했습니다. 사람의 확인은 되돌리기 어려운 변경에만, 알림은 할 일이 생기는 순간에만 쓰도록 설계했고, 그 원칙에 맞춰 도구를 붙였습니다.

남은 과제도 있습니다. 스키마를 ddl-auto 대신 Flyway 같은 마이그레이션 도구로 관리하면 DB 변경의 위험도를 더 낮출 수 있습니다. 실제 운영에서 알림 기준(5분에 10건)이 적절한지도 지켜보며 조정할 계획입니다.
