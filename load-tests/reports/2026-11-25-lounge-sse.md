# 2026-11-25 라운지 채팅(SSE) 몰림 측정

오픈 첫날처럼 접속자가 몰릴 때 라운지 실시간 채팅이 어떻게 버티는지 재고, 전송 구조를 고친 뒤 같은 조건으로 다시 쟀다. 운영 서버가 아니라 클라우드 개발 컨테이너의 `loadtest` 프로필 서버(로컬 PostgreSQL)에서 측정했다. 측정 도구는 [lounge-sse.mjs](../lounge-sse.mjs).

## 시나리오

| 이름 | 접속자 | 메시지 | 기타 |
| --- | --- | --- | --- |
| main | 300명이 10초에 걸쳐 연결하고 입장 | 보내는 사람 25명, 초당 약 10개, 60초 | 읽기가 느린 접속자 15명(휴대폰 데이터 흉내) |
| burst | 200명 | 보내는 사람 60명, 초당 33~37개, 40초 | 느린 접속자 15명 |

- 유실률: 연결돼 있던 접속자가 실시간으로 받아야 했던 (접속자, 메시지) 쌍 중 받지 못한 비율. 화면은 30초마다 목록을 다시 조회하므로 결국 보이지만 그만큼 늦게 보인다.
- 전달 시간: 보낸 시각부터 접속자가 받은 시각까지.
- 전송량: 접속자 1명이 받은 전체 바이트 ÷ 보낸 메시지 수(처음 목록, 입장 알림 포함).

## 결과

최신 `dev`(채팅 반응, 대화 기록 유지 포함)를 개선 전으로, 같은 코드에 이번 변경을 더한 것을 개선 후로 두고 같은 조건에서 쟀다.

### main (접속 300명, 초당 10개)

| 항목 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 실시간 연결 | **200명**(100명 거부, 503) | **300명**(거부 0) |
| 거부로 생긴 ERROR 로그 | 100건(약 10초 동안) | 0건 |
| 메시지 유실률 | 0.35% | 0% |
| 전달 시간 p95 (전체) | 2,014ms | **42ms** |
| 전달 시간 p99 (전체) | 8,622ms | 267ms |
| 전달 시간 p95 (느린 접속자 제외) | 52ms | 27ms |
| 메시지 1개당 접속자 1명 전송량 | 30,096B | **3,644B** (약 88% 감소) |
| 60초 동안 보낸 총량 | 3,444MB(200명) | 626MB(300명) |
| 백엔드 RSS | 579MB(200명) | 589MB(300명) |

### burst (접속 200명, 보내는 사람 60명) 두 번 측정

| 항목 | 개선 전 (1회 / 2회) | 개선 후 (1회 / 2회) |
| --- | ---: | ---: |
| 실제 전송 성공 | 초당 29.7개 / 29.3개 | 초당 37.5개 / 37.5개 |
| 메시지 유실률 | **7.7% / 5.8%** | **0% / 0%** |
| 전달 시간 p95 | 7,518ms / 6,952ms | **112ms / 113ms** |
| 전달 시간 p99 | 19,358ms / 19,207ms | 273ms / 273ms |
| 메시지 1개당 접속자 1명 전송량 | 12,373B / 12,586B | **831B / 831B** (약 93% 감소) |
| 보내기 거절(429) | 289건 / 291건 | 0건 |

개선 전에는 보내기 요청이 잠금 뒤에서 밀렸다가 한꺼번에 처리되며 "너무 빨리 보냄"(429)에 걸려, 같은 사람이 보낸 메시지도 일부 거절됐다.

## 원인과 개선

| 원인(개선 전 코드) | 개선 |
| --- | --- |
| 실시간 연결 상한 200명, 넘치면 `ResponseStatusException(503)` → 전체 예외 처리가 ERROR 로그를 남기고, 응답 형식 변환도 실패 | 상한을 환경변수(`LOUNGE_MAX_STREAMS`, 기본 1000)로. 넘치면 예외 없이 `full` 이벤트를 보내고 화면은 3초 조회로 바꿈 |
| 전송 스레드 1개, 대기열 64칸, 넘치면 가장 오래된 작업을 버림(`DiscardOldestPolicy`) → 메시지가 조용히 사라짐 | 접속자마다 대기열(256칸), 공용 스레드 4개. 넘친 연결은 끊고 다시 붙게 해서 처음 목록을 받음(조용한 유실 없음) |
| 느린 한 명에게 보내는 동안 나머지 모두가 기다림 | 접속자별 대기열이라 느린 사람은 자기 대기열만 밀림 |
| 새 글, 입장, 퇴장마다 최근 100개 전체와 참여자 목록을 모두에게 보냄 | 새 글은 그 글 하나(`message`), 입장과 퇴장은 참여자 목록만(`presence`). 전체 목록은 처음 연결과 목록 초기화 때만 |
| 접속자마다 같은 내용을 다시 JSON으로 만듦 | 한 번 만든 문자열을 모두에게 씀 |
| `stream`, 입장, 퇴장에 컨트롤러 전체 `synchronized` | 목록 읽기만 잠그고 나머지는 잠그지 않음 |

## 해석 범위

- 같은 머신에서 서버와 측정 도구가 함께 돌았다(CPU 4코어). 홈서버(노트북, 메모리 8GB) 숫자는 아니다.
- 개선 후 백엔드 RSS는 접속 300명에서 589MB로, 운영 백엔드 `mem_limit` 1GB 안이다.
- 새 글은 하나만 보내지만, 이모지 반응은 아직 전체 목록을 다시 보낸다(분당 횟수 제한이 있어 몰림 영향이 작다).
- 실제 오픈 날의 기록이 아니라, 몰림을 가정한 부하 시나리오다.
